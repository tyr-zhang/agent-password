# agent-pwd — AI integration contract

Generated by `agent-pwd docs`; do not edit by hand.

All action commands emit JSON by default. Secrets never appear in output.


## Commands


### Actions (AI)

- `agent-pwd api call --cred <id> --method GET --path /v1/x` — make an HTTP request with the stored token injected by the daemon
  flags: --cred --method --path --body --header --allow-redirect
- `agent-pwd env run --cred <id> -- <command...>` — inject an envvar credential into a child process and return redacted output
  flags: --cred
- `agent-pwd fill --cred <id> --field password|totp|username|token` — issue a one-shot, expiring handle; never returns the secret itself
  flags: --cred --field
- `agent-pwd fill apply --handle <h> -- <command...>` — consume a fill handle and inject the value into a child process via stdin/env
  flags: --handle
- `agent-pwd sql query --cred <id> -- "<SQL>" [--arg v]...` — execute SQL (mysql/postgres) or a read-only redis command
  flags: --cred --arg
- `agent-pwd ssh exec --cred <id> -- <command...>` — run a command over SSH using the stored credential, return redacted stdout
  flags: --cred --insecure-host-key

### Confirmation

- `agent-pwd confirm approve <id> [--no-biometric]` — approve a pending action via Touch ID / Windows Hello, falling back to master password
  flags: --no-biometric --password
- `agent-pwd confirm deny <id>` — reject a pending action
- `agent-pwd confirm result <id> --token <poll_token> [--wait]` — fetch the outcome of a confirmed action (one-shot final result)
  flags: --token --wait

### Management (human)

- `agent-pwd audit tail [--n 50]` — show the latest audit records (no secret material)
  flags: --n
- `agent-pwd audit verify` — verify the full audit hash chain
- `agent-pwd cred add <web|apikey|server|envvar> <label>` — interactively add a credential; secret fields never enter shell history
  flags: --secret --risk --tags --port
- `agent-pwd cred list` — list credential metadata
- `agent-pwd cred restore --from <backup>` — restore a vault backup after explicit human verification
  flags: --from
- `agent-pwd cred rm <id|label>` — delete a credential
- `agent-pwd cred show <id|label>` — show metadata only; there is no path that prints a secret
- `agent-pwd docs [--format md|json]` — print the AI integration contract generated from this command registry
  flags: --format
- `agent-pwd doctor` — check permissions, backups, audit chain, daemon and platform hardening
- `agent-pwd init` — initialize the vault and set the master password
  flags: --password --new-password
- `agent-pwd lock` — zeroize session keys and invalidate fill handles/pending actions
- `agent-pwd policy add --cred-pattern '<glob>' --action '<glob>' --decision allow|confirm|deny` — insert a policy rule at the front (new rules have highest priority)
  flags: --cred-pattern --action --decision --condition --id
- `agent-pwd policy list` — list rules in priority order
- `agent-pwd policy rm <id>` — remove a rule by id
- `agent-pwd rotate-password [--new-salt]` — change the master password (rewrap DEK only unless --new-salt)
  flags: --new-salt --password --new-password
- `agent-pwd service install` — install a per-user LaunchAgent / systemd unit / scheduled task
- `agent-pwd service status` — report autostart status
- `agent-pwd service uninstall` — remove the per-user autostart entry
- `agent-pwd status` — show daemon, session and KDF status (no secrets)
- `agent-pwd unlock` — unlock the session in the running daemon
  flags: --password
- `agent-pwd version` — print the agent-pwd build version
## AI integration contract

agent-pwd is a credential proxy: you can USE credentials but you cannot READ them.
Never try to print, dump, guess or exfiltrate a plaintext secret. There is no `cred show --secret`, no HTTP API, no MCP server and no command that returns a stored value.

### What you can do
- Run SSH commands, SQL queries, API calls, and child processes with an injected environment variable.
- Request a one-time `fill` handle for a trusted child process; the handle is useless to a human reader.
- Ask for confirmation when a high-risk action is required.
- Use credential labels with `--cred`; IDs are accepted for compatibility, and labels are matched first.

### What you cannot do
- `cred show` returns metadata only; reading vault.dat or audit.log never yields plaintext.
- Probing daemon memory or the IPC socket for keys is outside the CLI contract and will not help.
- You may not bypass, suppress, or auto-approve a confirmation request. If an action exits with code 10, STOP,
  surface the confirmation_id and poll token to a human, and do not retry until they approve it.

### JSON output shape
The CLI prints the result object directly, e.g. {"status": "unlocked", ...}. Failures print
{"ok": false, "error": {"code": 20, "message": "..."}}. On the daemon IPC wire the envelope is
{"ok": true, "result": {...}}, but callers never see that envelope.
`--human` switches to compact text; JSON is the default. Undeclared fields are never emitted.

### Exit codes
0 success; 10 pending confirmation (a confirmation_id is returned); 20 vault locked or daemon not running;
30 policy denied; 40 credential not found; 1 other error (see error.code).

### Pending confirmation workflow
1. The action command exits 10 and prints confirmation_id + poll_token. Do not retry.
2. A human runs `agent-pwd confirm approve <id>` (Touch ID / Windows Hello, or master-password fallback).
3. Run `agent-pwd confirm result <id> --token <poll_token>` once to collect the final outcome.
   Use --wait on the original action if you want the command to block until the human decides.
Pending actions live only in daemon memory: a daemon restart cancels them.

### Safety notes
- You may cause side effects through the commands you are allowed to execute (e.g. SQL writes or HTTP POSTs);
  the policy layer requires confirmation but cannot judge intent. Never treat these tools as permission to
  perform unrelated destructive actions.
- All actions are appended to a hash-chained audit log. Credentials can be removed or rotated immediately.
