# Localization (i18n)

Language: [English](i18n.md) · [简体中文](i18n.zh-CN.md)

agent-pwd translates only human-facing CLI text. Anything a program, script, or agent parses is a stable machine contract and stays in English.

## Supported languages and selection

| Code | Language |
|---|---|
| `en` | English — canonical source language and fallback |
| `zh-CN` | Simplified Chinese |

Selection precedence is:

1. `--lang <code>` (global flag; accepted before or after the command, but not after `--`)
2. `AGENT_PWD_LANG` environment variable
3. `en`

For example:

```bash
agent-pwd --lang zh-CN status
AGENT_PWD_LANG=zh-CN agent-pwd docs
```

`--lang` also accepts `--lang=<code>`. Input is trimmed and case-insensitive; the aliases `zh`, `zh-cn`, `zh_cn`, `zh-hans` and `zh_hans` map to `zh-CN`. Unsupported values fall back to `en`. The OS locale is never consulted, so generated output is deterministic. `make docs` sets `AGENT_PWD_LANG=en` and `AGENT_PWD_LANG=zh-CN` explicitly when generating the two contract files.

## Canonical English keys

The translation layer is in [`internal/i18n/i18n.go`](../internal/i18n/i18n.go) and the catalog is in [`internal/i18n/catalog.go`](../internal/i18n/catalog.go).

- Every call to `i18n.T(lang, key, args...)` uses the **exact English source string as the key**. English is the identity locale: `T(en, key)` returns `key` unchanged.
- `catalogZHCN` maps those canonical English keys to Simplified Chinese. If a key is absent, output falls back to the English key rather than failing.
- Command summaries, contract sections in [`internal/cli/docs.go`](../internal/cli/docs.go), and human-readable CLI messages are all keys. Editing the English wording creates a *new* key; update the catalog entry in the same change.
- Format arguments are expanded with `fmt.Sprintf`, so the key's placeholders are part of its identity and must match the call site.

## Translation rules

1. **Placeholder parity.** Keep every `%s`, `%d`, `%q`, `%%`, and any other format verb exactly as in the English key: same count, same order, same type. Do not add, drop, or reorder placeholders. A mismatch produces broken output at runtime.
2. **Backtick parity.** Backticks mark inline code in Markdown and in CLI text. Preserve the same number of backtick spans and their contents around commands, flags, paths, and literal values. Do not translate the text inside those spans.
3. **Flag parity.** Command names, subcommands, flag names, flag values, `<placeholders>`, and examples (for example `agent-pwd docs`, `--lang zh-CN`, `confirm approve <id>`, `--format md|json`) stay verbatim. Only the surrounding explanation is translated.
4. **Meaning and tone.** Match the English meaning precisely and keep messages concise; do not introduce new promises, behaviors, or security guarantees. When in doubt, keep the English text.

## Machine tokens that must NOT be translated

- **JSON keys and field names:** `ok`, `error`, `code`, `message`, `result`, `status`, `version`, `commands`, `exit_codes`, `contract`, `confirmation_id`, `poll_token`, and similar fields.
- **Enums and literal values:** `allow`, `confirm`, `deny`, `normal`, `high`, `md`, `json`, `en`, `zh-CN`, decision/outcome/result-code values, and other literal constants.
- **Exit codes:** `0`, `10`, `20`, `30`, `40`, `1` and their documented meanings as machine values.
- **Error codes:** `OK`, `PENDING`, `LOCKED`, `NO_DAEMON`, `DENIED`, `NOT_FOUND`, `BAD_ARGS`, `EXISTS`, `CORRUPT`, `TIMEOUT`, `BIOMETRIC_REQUIRED`, `INTERNAL`.
- **Command and flag names:** every command or subcommand in the registry, `--cred`, `--token`, `--human`, `--json`, `--lang`, `--format`, and all `--`-prefixed options.
- **Audit fields:** `seq`, `ts`, `credential_id`, `action`, `decision`, `confirm_source`, `outcome`, `result_code`, `detail_hash`, `policy_rule`, `client`, `prev_hash`, `hash`.
- **Diagnostics:** machine-facing identifiers, error-code strings, log field names, and stable tokens used in messages or matching stay in English. Only the human-readable prose around them may be translated through `T()`.

Do not translate secrets, hashes, credential IDs, tokens, file names, or platform paths either.

## How to add a language

Adding a locale is a code change, not only a catalog change:

1. Choose a language code (use a BCP-47-style code such as `fr`) and document it in the language table above and in contributor-facing docs.
2. In [`internal/i18n/i18n.go`](../internal/i18n/i18n.go), add a `Lang` constant, extend `ParseLang` with accepted aliases, and add the code to `Supported()`.
3. In [`internal/i18n/catalog.go`](../internal/i18n/catalog.go), add a `catalogXX` map and extend `T()` to select it. Keep `en` as the identity fallback; do not add OS-locale detection.
4. Enumerate all current `i18n.T` keys and add translations for the new catalog. Missing keys fall back to English; tests or a coverage check should flag omissions.
5. Update the `--lang` help text and any prose that enumerates supported languages.
6. If the generated AI contract should include the new language, extend the `docs` and `docs-check` targets in the [`Makefile`](../Makefile) so they generate and diff a `docs/contract.<code>.md` file.
7. Add tests in `internal/i18n` and `internal/cli` for parsing, fallback, placeholders, and generated docs.

## Useful commands

```bash
make i18n-check   # go test ./internal/i18n ./internal/cli
make docs         # regenerate docs/contract.md and docs/contract.zh-CN.md
make docs-check   # fail if generated contract files are out of sync
make test         # full unit, integration, and security-regression suite
make vet
make race
make cross
```

`make docs-check` generates fresh contract files into `/tmp` and diffs them against the checked-in files. Commit regenerated docs together with any translation or command-surface change.
